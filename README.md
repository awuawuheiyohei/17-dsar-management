# DSAR Management Platform

> GDPR Art. 12–22 数据主体请求（Data Subject Access Request）的全生命周期管理平台
> 身份核验 → 法定时限倒计时 → 跨系统检索编排 → 脱敏响应 → 留存销毁 → 全链路审计

## 核心叙事：隐私合规不是发邮件，是有流程、有时限、有审计的系统工程

个人在社交平台点一下「删除我的账号」，背后是一串带法律后果的工程问题：

1. **你到底是不是他？** —— 核验失败就处理，等于把所有人的数据开放给任何自称的人
2. **什么时候必须答复？** —— GDPR Art. 12(3) 给了硬期限，算错就是可被处罚的违规
3. **数据散落在哪些系统？** —— 一个主体可能出现在 CRM、HR、订单、分析仓库等 6–8 个系统里
4. **凭什么拒绝？** —— Art. 12(4) 要求告知理由，Art. 17(3) 规定了合法的除外情形
5. **交出去的数据要不要脱敏？** —— Art. 15 要求完整，但 Art. 15(4) 禁止损害他人权利
6. **响应本身含个人信息，谁来销毁它？** —— 很多 DSAR 系统漏掉这一环

本项目把这六件事做成了**可配置、可审计、可测试的系统控制**，而不是流程文档里的口头约定。

## GDPR 条款 ↔ 请求类型对照

平台支持的 7 类请求（`GET /api/rights` 是唯一事实来源，UI 下拉框、API 校验、测试断言都读它）：

| 请求类型 | 中文 | GDPR 条文 | 常见期限 | CCPA / CPRA 对应机制 |
|---|---|---|---|---|
| `ACCESS` | 访问权 | **Art. 15** | 1 个月 | Know（§1798.100 / §1798.110） |
| `RECTIFICATION` | 更正权 | **Art. 16** | 1 个月 | Correct（§1798.106） |
| `ERASURE` | 删除权 | **Art. 17** | 1 个月 | Delete（§1798.105） |
| `RESTRICTION` | 限制处理权 | **Art. 18** | 1 个月 | Limit Use of Sensitive PI（§1798.121） |
| `PORTABILITY` | 可携权 | **Art. 20** | 1 个月 | 无直接对应 |
| `OBJECTION` | 反对处理权 | **Art. 21** | 1 个月 | Opt-out of Sale/Sharing（§1798.120） |
| `AUTOMATED_DECISION` | 自动化决策人工介入 | **Art. 22** | 1 个月 | CPRA 范围内 ADMT |

辅助条款在代码中的落点：

| 条款 | 要求 | 本项目实现位置 |
|---|---|---|
| Art. 12(3) | 收到后 1 个月内答复；复杂情形可延长 2 个月，**但须在同一期限内通知** | `deadlines.extension_is_valid` |
| Art. 12(4) | 拒绝须告知理由，且须在合理期限内 | `denial_reasons` 受控词表 + `POST /api/requests/{id}/deny` |
| Art. 12(5) | 明显无依据或重复的过度请求可收费或拒绝 | `ART_12_5_REPEATED` |
| Art. 12(6) | **核实身份后方可处理**；补充信息期间时钟暂停 | `verification.py` + `workflow.GUARDS` + `clock_stop` |
| Art. 15(3) | 数据副本须以通用机器可读格式提供 | `format: JSON / CSV / SECURE_LINK` |
| Art. 15(4) | 不得损害他人的权利与自由 | `redaction` 第三方数据剥离 |
| Art. 17(3) | 删除权的除外情形（法律义务、法律主张、公共利益等） | `ART_17_3_A/B/E` 拒绝理由 |
| Art. 5(1)(c) | 数据最小化 | 字段级脱敏 + 响应留存期 |
| Art. 5(1)(e) | 存储限制 | `retention_policies` + `POST /api/retention/purge` |
| Art. 5(2) | 问责制 | `audit_log` 全链路只追加审计 |
| Art. 9 | 特殊类别数据（健康/政治/种族/宗教） | 默认**不在响应中交付**，仅记录存在性 |

## 法定时限：最容易写错的地方

GDPR Art. 12(3) 的表述是「**一个月**（one month）」，不是 30 天。按对应日计算并做**月末截断**：

```
2026-01-31 + 1 个月 = 2026-02-28    ← 平年 2 月无 31 日
2024-01-31 + 1 个月 = 2024-02-29    ← 闰年
2026-08-31 + 1 个月 = 2026-09-30
2026-12-31 + 2 个月 = 2027-02-28    ← 跨年
```

朴素实现（「减一天再加一个月」）会算出 2026-03-03，比法定日期晚了 3 天。
本项目自己实现 `add_months()` 而不引入 `dateutil`，就是为了让每个边界都能被单测覆盖
（`tests/test_deadlines.py` 里有 20+ 个月末/闰年/跨年/负月数用例）。

**延长必须留通知证据。** Art. 12(3) 允许复杂情形延长两个月，但条件是「在同一期限内通知数据主体」。
所以本项目的设计是：**没有合法的通知记录，延长不予采信**，到期日仍按原始期限算，
并在 `warnings` 里说明原因。系统不会因为「我已经决定延期」就自动给请求宽限。

**时钟暂停（Art. 12(6)）必须建模。** 向数据主体索取补充信息期间期限暂停。
若不实现这一条，所有「已向对方索要信息」的请求都会被误判为超期。

法域策略（`GET /api/deadlines/policies`，可配置、可测试）：

| 法域 | 法规 | 期限 | 可延长 | 时钟暂停上限 |
|---|---|---|---|---|
| EU | GDPR Art. 12(3) | 1 个月 | +2 个月 | 60 天 |
| UK | UK GDPR Art. 12(3) | 1 个月 | +2 个月 | 60 天 |
| CA | CCPA §1798.130(a)(2) | 45 天 | +45 天 | 45 天 |
| CN | PIPL 第 50 条 | 15 天 | 不可延长 | 30 天 |

## 状态机

```
                          ┌──────────────┐
                          │  RECEIVED    │  受理即起算期限（Art.12(3)）
                          └──────┬───────┘
                                 ▼
                    ┌────────────────────────┐
                    │ IDENTITY_VERIFICATION  │  Art.12(6) 核实身份
                    └────┬──────────────┬────┘
         identity VERIFIED │              │ 核验失败 / 无法处理
                    ┌──────▼───────┐      │
                    │ IN_PROGRESS  │      │         ┌──────────┐
                    └──┬────────┬──┘      └────────►│  DENIED  │ 须附法定理由
                       │        │                 └────┬─────┘
        需补充信息      │        │ 检索任务全部收敛      │ 申诉可重开
              ┌────────▼──────┐ │ ＋已生成响应         └──► 重新进入流程
              │CLARIFICATION_ │ │                                 
              │  REQUESTED    │ │        ┌──────────┐              ┌──────────┐
              └───────┬───────┘ │        │ COMPLETED│              │ WITHDRAWN│
                      ▼         │        └──────────┘              └──────────┘
             ┌──────────────────┴──┐            ▲                    （终态）
             │ CLARIFICATION_      │────────────┘
             │      ANSWERED       │   部分系统被法定排除
             └─────────────────────┘            │
                                       ┌────────▼────────┐   ┌─────────┐
                                       │PARTIALLY_COMPLETED│   │ EXPIRED │
                                       └──────────────────┘   └─────────┘
```

**Guard 前置条件**（不满足则拒绝流转，并在 400 的 `detail.reasons` 中说明是哪条规则挡住了）：

| 流转 | 前置条件 |
|---|---|
| `* → IN_PROGRESS` | 身份核验状态必须是 `VERIFIED` |
| `IN_PROGRESS → COMPLETED` | 核验通过 **且** 检索任务 `open_count == 0` **且** 已生成响应 |
| `IN_PROGRESS → DENIED` | 必须有 `reason_code` **且** 说明 ≥ 10 字符 |
| `IN_PROGRESS → CLARIFICATION_REQUESTED` | 身份核验必须已通过 |

任务级状态机同样禁止跳步：`PENDING → COMPLETED` 非法，必须 `PENDING → RUNNING → COMPLETED`。
`COMPLETED` / `NOT_FOUND` / `EXCLUDED` 是**冻结终态**，误标不可覆盖，只能新建任务 —— 保证审计链不被改写。

## 身份核验：默认拒绝

三段式判定，避免「差一点点」被自动放行：

1. **方式强度**（0–100）：账户内二次认证 100 > 证件核验 95 > 邮箱 OTP 90 > 短信 OTP 85 > 邮寄信函 70 > 未核验 0
2. **风险信号扣分**：姓名不符 −25、第三方代为请求 −30、邮箱域不符 −20、历史失败 −15、不可逆请求类型 −10……
3. **阈值分档**：`≥80` 自动通过 ／ `60–79` **转人工复核** ／ `<60` 拒绝

另外强制：OTP 有效期 15 分钟（防重放，过期即失效）、最多 3 次尝试（防暴力猜解）、
人工复核**必须填写依据说明**（「人工放行」本身是需要留痕的审计事件）。

> 关键点：`MANUAL_REVIEW` **不允许**披露数据。置信度不足不等于可以放行。

## 数据最小化：响应本身也是个人信息

导出的响应不是数据库行的直接 dump，而是三步处理（`app/models/redaction.py`）：

1. **字段级敏感识别** —— 按字段名 + 值形态双重判定（16 位数字还要过 **Luhn 校验**才认定是卡号）
2. **按模式脱敏** —— 邮箱 `a***@e***.com`、手机号保留末 4、证件号只留末 4、卡号直接 token 化
3. **第三方数据剥离** —— 记录里的紧急联系人、共同账户人、经理姓名等**不属于本主体**的信息一律移除（Art. 15(4)）

**Art. 9 特殊类别数据（健康、政治、种族、宗教）默认不在响应中交付**，
只写 `health_conditions_presence: "WITHHELD_SPECIAL_CATEGORY_ART9"`。
因为把这类数据直接交出去，本身就可能违反 Art. 9 的处理限制 —— 需要单独法律评估。

`redaction_mode=NONE` 被 API 层直接拒绝（400），不允许对外交付未脱敏响应。

## 跨系统检索编排

一个数据主体可能同时出现在 8 个系统里。`POST /api/requests/{id}/discover` 按
`request × source × category` 生成任务计划（演示数据下 8 × 8 = 64 个任务）。

- **幂等** —— 确定性 `task_id`（SHA1 of request|source|category）+ `UNIQUE` 索引，重复触发不产生重复任务
- **法定排除不是静默跳过** —— 默认排除的源（如冷备份归档）直接落 `EXCLUDED` 并携带依据
  `Art. 17(3)(b) 履行法律规定的留存义务`，排除本身可解释、可审计
- **覆盖率按「已收敛任务」计算**，排除项算已处理，否则有留存义务的系统会让请求永远关不掉
- **未收敛阻塞关闭** —— `open_count > 0` 时不允许把请求标记为 `COMPLETED`

| GET | `/api/requests/{id}/tasks` | 检索任务 + 收敛汇总 |
| PATCH | `/api/tasks/{tid}` | 更新任务状态（含业务约束校验） |
| POST | `/api/requests/{id}/response` | 生成脱敏响应（带留存到期日） |
| GET | `/api/responses` | 响应交付列表（**不返回完整载荷**） |
| POST | `/api/retention/purge` | 销毁到期响应（数据最小化执行点） |
| GET | `/api/audit` | 审计日志（按 action / entity 过滤） |

交互式文档：`http://127.0.0.1:5054/docs`

## 拒绝（Denial）的受控词表

不能自由发挥 —— 拒绝理由必须落在预置词表内，且按请求类型限定适用范围：

| reason_code | 条款 | 理由 | 需要审批 | 适用范围 |
|---|---|---|---|---|
| `ART_15_4` | Art. 15(4) | 涉及他人权利与自由 | ✅ | ACCESS, PORTABILITY |
| `ART_17_3_A` | Art. 17(3)(a) | 履行法律规定的义务 | ✅ | ERASURE |
| `ART_17_3_B` | Art. 17(3)(b) | 为法律主张所必需的留存 | ✅ | ERASURE |
| `ART_17_3_E` | Art. 17(3)(e) | 公共利益或科学研究 | ✅ | ERASURE |
| `ART_19_ABSENT` | Art. 19 | 通知接收方的义务无法履行 | ✅ | ERASURE, RECTIFICATION |
| `ART_12_5_REPEATED` | Art. 12(5) | 重复或无依据的过度请求 | — | 全部 |
| `ART_21_COMPELLED` | Art. 21(1) | 存在强制性法律依据 | ✅ | OBJECTION |
| `IDENTITY_FAILED` | Art. 12(6) | 身份核验未通过 | — | 全部 |
| `NO_MATCHING_DATA` | Art. 12(4) | 未检索到匹配数据 | — | 全部 |
| `OUT_OF_SCOPE` | Art. 12(4) | 超出控制者管辖范围 | — | 全部 |

拒绝必须同时满足：`reason_code` 命中词表 → 适用当前请求类型 → 需要审批的须填 `approved_by`
→ 说明 ≥ 10 字符（要求法律依据的 ≥ 20 字符）。拒绝后未收敛的检索任务全部落 `EXCLUDED` 并留依据。

## 审计与留存

**审计**（`audit_log`，只追加不修改）：谁请求、谁核验、谁批准、检索了哪些系统、
返回了什么、谁拒绝的、依据哪一条、谁销毁的。每个变更动作都有 `actor` + `actor_role`
（`DATA_SUBJECT` / `ANALYST` / `PRIVACY_OFFICER` / `SYSTEM`）。

**留存**（`retention_policies`）：

| 制品 | 留存 | 法律依据 |
|---|---|---|
| 响应载荷 | 30 天 | Art. 5(1)(e) 存储限制 |
| 身份核验证据 | 180 天 | Art. 5(1)(e) + 举证责任 |
| 检索执行留痕 | 365 天 | Art. 5(2) 问责制 |
| 拒绝记录 | 3 年 | Art. 12(4) + 举证责任（在控制者） |
| 审计日志 | 3 年 | Art. 5(2) 问责制 |

`POST /api/retention/purge` 执行销毁：载荷置空 + 状态 `PURGED` + 记录 `purged_at`，
**不抹除痕迹** —— 审计链仍能证明「这份数据曾交付、已按期销毁」。

## 开发中踩到并修掉的缺陷

| # | 缺陷 | 现象 | 修复 |
|---|---|---|---|
| 1 | 期限快照漏算时钟暂停 | 入库 `due_date` 是受理时算的原始期限，`build_deadline_view` 直接读取它，导致 Art. 12(6) 暂停天数**完全没生效** —— 索要过补充信息的请求被误判超期 | 在 `deadlines.build_deadline_view` 统一叠加暂停天数（受法域上限约束），并补测试 `test_clock_stop_extends_effective_due_date` |
| 2 | 拒绝后请求永远关不掉 | 拒绝时把未收敛任务批量置 `WAIVED`，但 `WAIVED` 在模型里是**阻塞态**（待人确认的豁免），导致 `open_count` 永不为 0，请求无法关闭 | 改为 `EXCLUDED`（收敛态），并写明依据条款；补 `test_denial_closes_open_tasks` |
| 3 | 延长校验逻辑自相矛盾 | `build_deadline_view` 里为「检查延期是否合法」反过来调 `extension_is_valid`，其中又要求填写理由 —— 而回看快照时库里本就有理由，产生死循环式重复校验和错误回落 | 拆出 `require_reason` 参数：回看场景只校验通知证据的时效，不重复要求理由 |
| 4 | 未知风险信号静默失效 | 核验评估对无法识别的信号直接跳过，调用方拼错字符串（如 `"mail_mismatch"`）时会**无声地少扣分**，看起来更安全实则是绕过 | API 层在进入引擎前校验信号合法性并返回 400；引擎内保留忽略逻辑并加注释说明 |
| 5 | 任务不能从 PENDING 直接完成（测试自身踩坑） | 自己的测试辅助函数直接 `PATCH status=COMPLETED` 全部静默失败，随后断言「终态不可回退」却拿到 200 | 辅助函数改为走 `PENDING → RUNNING → 终态`，顺带把「必须先真正开始检索」这条约束写进测试 |
| 6 | `summarize_tasks` 遇缺字段 KeyError | 任务字典缺少 `status` 键时 `t["status"]` 直接抛异常，而不是回落到默认 `PENDING` | 改用 `t.get("status", "")` |
| 7 | 「今日到期」演示数据会随日期漂移 | 原来写死「29 天前受理」，换一天跑就不再是 `DUE_TODAY`，smoke test 的断言会时好时坏 | 改为 `add_months(today, -1)` 计算接收日，到期日恒等于当天 |
| 8 | 记录挂在请求上导致数据虚增 | `data_subject_records` 按 request 生成，同一个人有多个请求时数据重复 | 修正为按 requester 生成（数据客观存在于系统中，与是否发过请求无关） |
| 9 | 邮箱无点域名被误判 | `a@localhost` 走 `rpartition(".")` 后域部分被清空成 `a***@***`，丢失了本机/内网域信息 | 无 TLD 时保留完整域部分，并补测试固定该行为 |

## 不做什么（明确边界）

这是一个流程与控制的演示系统，以下**明确不在范围内**：

- **不做身份认证与授权** —— 没有登录、没有 RBAC、没有 API Key。生产环境必须先解决「谁能操作这个平台」
- **不做真实系统连接器** —— 不对接任何 HR / CRM / 订单 / 分析系统的 API 或数据库
- **不做加密** —— 演示数据本身是合成的，无加密需求。真实个人数据必须静态加密 + 密钥管理
- **不做邮件/通知投递** —— 不发送真实邮件或短信；OTP 有效期只做逻辑校验，不实际发码
- **不做文件级响应导出** —— 只有 JSON 载荷，CSV 与安全链接只是枚举值，没有实现对应生成器
- **不做 DPIA / TIA** —— 不做数据保护影响评估或传输影响评估
- **不做多租户 / 权限隔离** —— 单一组织模型
- **不做 CCPA 45 天「确认收到」两段式时限** —— 简化为从 `received_date` 起算
- **不做 PIPL 工作日与法定节假日计算** —— CN 时限按自然日近似（已在接口 `notes` 与本文档中标注）
- **不做 GDPR Art. 22 的自动化决策模型本身** —— 只实现「请求人工介入」这一权利的流程，不含决策逻辑
- **不做前端构建** —— Dashboard 是单文件原生 JS，无 TypeScript、无打包、无框架
- **不构成法律意见** —— 所有条款引用用于说明设计依据，实际合规判断须由法务与隐私官作出

## 技术栈与工程选择

| 选择 | 理由 |
|---|---|
| Python 3.11+ / FastAPI | 自带 OpenAPI 文档，隐私团队能直接看到每个端点的合规语义 |
| SQLite（WAL + busy_timeout + FK ON） | 零外部依赖即可完整演示；`DB_PATH` 环境变量支持测试隔离 |
| 纯标准库实现月加法 | 不引入 `dateutil`，让每个月末/闰年边界都能被单测钉死 |
| 手写 urlencoded 解析 | 避免 `python-multipart` 依赖，同时把「`+` 应解码为空格」这类细节变成可测行为 |
| 业务规则下沉为纯函数 | 每条合规规则可直接单测，不必绕 HTTP；路由层不重复实现规则 |
| 确定性 task_id + UNIQUE 索引 | 编排幂等靠约束保证，不靠调用方自觉 |
| 单文件原生 JS Dashboard | 打开即用，无 node_modules，无构建步骤 —— 评审者 clone 下来就能跑 |
